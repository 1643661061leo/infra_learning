
> 范围：本文讨论推理阶段常见的 DP、DP Attention、PCP、DCP、TP、PP、EP。性能结论是方向性判断，不是固定倍数；真实效果取决于模型结构、ISL/OSL、batch、并发、网络、kernel 和调度器。

## 1. 统一坐标系

设 Transformer 输入和模型结构为：

```text
X: [B, S, H]

B = batch / 请求维
S = sequence length
H = hidden size
L = Transformer layer 数
E = MoE expert 数
```

Attention 中还要区分：

```text
S_q  = 当前需要计算的 Query token 数
S_kv = 已有 KV Cache 的上下文长度
Nq   = Query head 数
Nkv  = KV head 数
Dh   = head_dim
H    = Nq × Dh
```

并行策略可以先记成：

```text
B / request       -> DP、DP Attention
S_q（Prefill）    -> PCP
S_kv（Decode）    -> DCP
H / head / matrix -> TP
L / layers        -> PP
E / experts       -> EP
```

但这些策略不全是简单的 Tensor `split()`：

- DP/DPA 是把不同请求路由给不同副本或 Attention shards；
- PP 是把不同层模块放到不同设备；
- EP 是按 expert ID 放置权重，再根据 gate 动态路由 token；
- PCP/DCP 都涉及序列维，但切的是不同阶段、不同 Tensor。

## 2. 指标是由什么构成的

### 2.1 TTFT

```text
TTFT =
Queue Time
+ 输入预处理/tokenization
+ Prefill Attention
+ Prefill MLP/MoE
+ 并行通信与同步
+ KV Cache写入/传输
+ 第一次Decode
+ sampling与首token输出
```

并行策略只有在它优化的部分占 TTFT 比例较高时，才会显著改善 TTFT。

### 2.2 TPOT / ITL

```text
TPOT ≈ 平均每个输出token的时间

每个token时间 =
等待下一次Decode调度
+ Decode Attention与KV读取
+ MLP/MoE
+ 并行通信
+ sampling/输出
+ Prefill或其他请求造成的干扰
```

TPOT 是平均生成速度；ITL 是相邻 token 的实际间隔，更容易暴露抖动和长尾。

### 2.3 吞吐

```text
系统吞吐 ≈ min(
  计算能力,
  HBM带宽,
  KV容量,
  GPU互联/网络,
  调度与负载均衡能力
)
```

扩大理论算力不一定增加吞吐；如果新的瓶颈变成通信、KV 容量或负载不均，扩展效率会下降。

### 2.4 KV Cache

标准 Attention 的 KV Cache 大小近似为：

```text
KV bytes ≈
2 × L × B × S_kv × Nkv × Dh × bytes_per_element
```

其中 `2` 代表 K 和 V。MLA 使用压缩 latent，具体公式不同，但仍随 batch、上下文长度和层数增长。

## 3. 总览表

| 策略           | 主要切分维度           | TTFT              | TPOT                 | 吞吐                 | 单 rank KV Cache      |
| ------------ | ---------------- | ----------------- | -------------------- | ------------------ | -------------------- |
| DP           | 请求/`B`           | 可能↓（排队减少）         | 可能↓（竞争减少）            | **↑**              | 可能↓（请求分流；不切单请求 KV）   |
| DP Attention | Attention 请求/`B` | 可能↓（高负载长尾）        | 可能↓（高并发）             | **↑**              | **↓**（减少同请求 KV 重复）   |
| PCP          | Prefill `S_q`    | **↓**             | 可能↓（减少 Prefill 阻塞）   | 可能↑（长 Prefill）     | 可能↓（仅部分 KV 路径）       |
| DCP          | Decode `S_kv`    | 可能↑（建 cache/通信）   | 可能↓（长上下文）            | **↑**              | **↓**（理想约 `1/DCP`）   |
| TP           | `H`、heads、矩阵维    | 可能↓（计算分摊）         | 可能↑（高 TP 通信）         | 可能↑                | ↓，直到 `TP=Nkv`；之后→    |
| PP           | 层数 `L`           | 可能↑（stage/bubble） | 可能↑（pipeline bubble） | 可能↑（足够 microbatch） | **↓**（只保存本 stage 的层） |
| EP           | expert 维 `E`     | 可能↓（大 Prefill）    | 可能↑（小 batch A2A）     | **↑**              | →（不直接切 Attention KV） |

## 4. DP：按请求切整个模型副本

### 切分方式

```text
Replica 0: request batch 0
Replica 1: request batch 1
...
```

整模型在不同副本中复制；每条请求只进入一个副本。

### 对 TTFT

- 不减少一条请求的 Prefill/Decode 计算；
- 低负载、无排队时，TTFT 基本不变；
- 高负载时多个副本分摊请求，Queue Time 和 P95/P99 TTFT 会下降；
- 路由不均或 prefix cache locality 变差，可能抵消收益。

### 对 TPOT

- 单请求 Decode kernel 通常不因 DP 直接变快；
- 不同副本的请求竞争减少，可间接改善 TPOT/ITL；
- 每个副本 batch 太小可能降低 GPU 利用率。

### 对吞吐

- 请求足够多时，吞吐可接近副本数线性增加；
- 会复制整模型权重，超大模型或 MoE 模型成本很高；
- 路由、负载均衡和 cache-aware 策略决定实际扩展效率。

### 对 KV Cache

- 不切一条请求的 KV；
- 同一请求通常只在一个副本保存，不跨 DP 副本重复；
- 每个副本有独立 KV pool，系统总 KV 容量随副本数增长；
- 副本内部若仍使用高 TP，仍可能存在 TP 导致的 KV 重复。

---

## 5. [[DP ATTENTION(DPA)]]：只在 Attention/KV 上按请求做 DP

### 切分方式

```text
Attention：不同 DP ranks 处理不同请求
FFN/MoE：  继续使用全局 TP/EP 权重
```

如果：

```text
T = tp_size
D = Attention dp_size
C = attn_cp_size
```

则 SGLang 中典型关系为：

```text
Attention TP size = T / (D × C)
```

### 对 TTFT

- DPA 的首要目标不是 Prefill 加速；
- Attention 本地化可能减少部分 TP 通信；
- 但 Attention 与 FFN/MoE 边界需要 gather、reduce-scatter 或 A2A；
- 高并发下 KV 容量和排队改善，P95 TTFT 可能明显下降；
- 小 batch、低延迟场景可能因同步与小 GEMM 变慢。

### 对 TPOT

- MLA Decode 中，减少 KV 重复后能承载更大有效 batch；
- 纯 DPA Attention 内部可以避免跨 Attention DP ranks 的 TP collective；
- 不同 ranks 同时处于 Prefill、Decode、idle 时，进入共享 MoE 的同步点可能产生等待；
- 因此高并发吞吐常改善，但单请求/低 batch TPOT 不保证下降。

### 对吞吐

- 对 DeepSeek、Kimi、MiniMax 等 MLA/MoE 模型通常收益明显；
- 释放 KV 显存后可提高 `max_running_requests` 和 Decode batch；
- EP、DeepEP、EPLB、Two-Batch Overlap 会影响最终收益；
- DP ranks 负载不均时，最慢 rank 会造成同步长尾。

### 对 KV Cache

普通 `TP=8`、MLA 单 KV latent 时，同一批请求的 KV 可能复制 8 份。

开启 `DP Attention=8`：

```text
每 GPU 处理约 B/8 条不同请求
每 GPU KV：[B/8, S, Ck]
```

固定总 batch 下，单 rank KV 理想约降为 `1/8`。但一条请求仍完整属于一个 Attention DP shard，所以 DPA 不能解决单请求超长 KV 跨卡放置。

## 6. PCP：切 Prefill 的 Query/token 序列

### 切分方式

```text
全局 Prefill Q：[B,S,Nq,Dh]

PCP=P 后每 rank：
Q_local：[B,S/P,Nq,Dh]
```

常见 Attention 路径：

```text
Partial Q + Full KV：AllGather K/V
Partial Q + Partial KV：Ring Attention
```

### 对 TTFT

- 这是 PCP 的主要优化指标；
- Dense Attention 的长序列计算随 `S²` 增长，长 Prompt 更容易覆盖通信成本；
- 理想模型：`Prefill compute/P + communication + imbalance`；
- 短 Prompt 下 AllGather、Ring、同步可能抵消计算收益；
- 因果 Attention 若切分不均，需要 zigzag/interleave/round-robin 平衡工作量。

### 对 TPOT

- PCP 不直接切 Decode KV，所以不是 Decode 加速策略；
- colocated serving 中，Prefill 变短可减少对 Decode batch 的阻塞，间接改善 P95 TPOT/ITL；
- 严格 P/D 分离时，若只改变 Prefill 节点，Decode kernel 本身不应因此变快；
- 部分框架的 PCP KV 布局可能给 Decode 增加额外重排/通信。

### 对吞吐

- 能提升单条或少量超长 Prompt 的 Prefill 并行度；
- 会为单请求占用更多 GPU，可能减少可用于 DP 副本的资源；
- 适合 TTFT/SLO 主导的长上下文场景，不一定提高短请求总吞吐。

### 对 KV Cache

- Partial-Q + Full-KV 路径在每 rank 收集完整 K/V，不天然节省 KV 峰值；
- Ring/Partial-KV 算法可让工作集沿序列分片；
- 持久化 Decode KV 是否按 PCP 分片取决于框架实现，不能由 `PCP=P` 直接推断为 `KV/P`。

## 7. DCP：切 Decode 历史 KV 序列

### 切分方式

Decode 本轮新 Query 数 `M` 通常为 1：

```text
Q：[B,M,Nq,Dh]                 # M通常不切
KV全局：[B,S_kv,Nkv,Dh]

DCP=D 后每 rank：
KV_local：[B,S_kv/D,Nkv,Dh]
```

每 rank 计算本地 KV shard 的局部 Attention，再使用 LSE 精确合并。

### 对 TTFT

- 不是主要 TTFT 优化手段；
- Prefill 建立分片 KV、cached/chunked prefill 可能需要额外通信；
- 如果没有 DCP 单卡根本放不下上下文，DCP 能把“无法完成”变成“可完成”；
- 真正只比较可运行配置时，TTFT 可能持平或因通信增加。

### 对 TPOT

正向因素：

```text
每 rank 只读取 S_kv/D 的KV
局部Attention工作量和HBM读取下降
```

负向因素：

```text
每个Decode token
× 每个Attention layer
都要做Q/输出/LSE相关通信
```

因此：

- 长上下文、KV 读取主导时更可能获益；
- 短上下文、小 batch、慢互联时可能让 TPOT 变差；
- DCP size 越大，KV 越省，但 collective 延迟越高。

### 对吞吐

- 单卡 KV 占用下降后可以扩大 batch 和并发；
- 对 MLA/MQA/少 KV-head 模型尤其有用；
- 总吞吐收益常大于单请求 latency 收益；
- 网络拓扑、DCP group 是否跨节点非常关键。

### 对 KV Cache

理想情况下：

```text
单 rank KV ≈ 原来的 1/D
```

例如 `Nkv=4, TP=8` 时，每个 KV head 在两个 TP ranks 上重复；`DCP=2` 可以让这两个 ranks 各保存一半 `S_kv`，从而去掉两份完整 KV 的重复。

单 GPU 不能执行真正的 `DCP>1`；单卡应使用 KV 量化、offload、压缩或减少上下文。

## 8. TP：切 hidden/head/矩阵维

### 切分方式

TP 不是只切一个激活 `H`，而是切模型矩阵的输入/输出维：

```text
Q heads：       Nq -> Nq/T
KV heads：      Nkv -> Nkv/T（直到不能再切）
MLP intermediate：I -> I/T
LM Head vocab： V -> V/T
```

典型列并行和行并行 Linear 会引入 AllGather、AllReduce 或 ReduceScatter。

### 对 TTFT

- Prefill GEMM/Attention 计算可分摊，模型计算占主导时 TTFT 下降；
- 每层通信增加，跨节点或小矩阵时扩展效率下降；
- TP 还能让原本单卡放不下的模型运行，这是容量收益。

### 对 TPOT

- Decode 每步 token 少，GEMM 较小，切得过细会降低 Tensor Core 利用率；
- 每层 AllReduce 延迟容易成为 TPOT 瓶颈；
- 适中的 TP 可降低权重读取/计算，过高 TP 常使低 batch TPOT 变差。

### 对吞吐

- 让大模型跨多卡放置；
- 同一请求占用更多 GPU，可能减少 DP 副本数；
- 高 batch 时大 GEMM 更容易获得良好扩展；
- 高 TP 下通信、矩阵碎片和 head 对齐会限制吞吐。

### 对 KV Cache

若 `TP <= Nkv` 且能整除：

```text
每 rank KV heads ≈ Nkv/TP
单 rank KV 约随 TP 下降
```

若 `TP > Nkv`：

```text
KV head不可再切
复制倍数 ≈ TP/Nkv
```

例如 `Nkv=4, TP=8`：KV0～KV3 各复制两份，整个 TP group 的 KV 总量是逻辑需求的 2 倍。

## 9. PP：切模型层数

### 切分方式

```text
PP stage 0：layers 0  ～ L/4-1
PP stage 1：layers L/4～ L/2-1
PP stage 2：...
PP stage 3：最后一组layers
```

stage 之间发送 hidden states `[B,S,H]` 或 packed token activation。

### 对 TTFT

- 一条请求仍必须顺序经过所有 stages；
- 增加 stage 间传输和流水线 bubble，单请求 TTFT 通常不会降低；
- 足够多 microbatches 时可以重叠不同请求/微批次，但首个微批仍要走完整流水线。

### 对 TPOT

- 每个生成 token 都要经过所有 pipeline stages；
- Decode batch 太小会产生严重 bubble；
- 高并发、多个 microbatches 可让 stages 持续工作，改善吞吐但未必改善单请求 TPOT。

### 对吞吐

- 主要价值是把超大模型按层放到多卡/多节点；
- 吞吐依赖 microbatch 数量、stage 计算均衡和调度；
- 最慢 stage 决定稳态吞吐。

### 对 KV Cache

- 每个 stage 只保存自己层的 KV；
- 固定请求下，若层均匀切分，单卡 KV 约随 `1/PP` 下降；
- 整个 pipeline 合计 KV 总量不变；
- PP 不切 batch、单层 head 或单层序列长度。

---

## 10. EP：切 experts，不是固定切 S/H

### 切分方式

MoE 输入先展平：

```text
X：[B,S,H] -> [T,H]
T = B × S
```

`E` 个 experts 分布到 `EP` 个 ranks：

```text
每 rank 约持有 E/EP 个 experts
```

Gate 为每个 token 选择 top-k experts：

```text
token 0 -> expert 3、80
token 1 -> expert 17、200
```

EP 使用 All-to-All Dispatch 把 token 行 `[1,H]` 发给对应 expert，计算后再 All-to-All Combine 返回原位置。

### 对 TTFT

- Prefill token 多，expert GEMM 较大，EP 能分摊专家权重和计算；
- A2A 通信与 expert 负载不均会增加长尾；
- 热门 expert 或跨节点网络不足时，最慢 expert rank 决定 Prefill 时间。

### 对 TPOT

- Decode 每步每请求 token 很少，expert GEMM 小，A2A latency 更突出；
- batch 足够大时，expert GEMM 和通信更容易摊薄；
- EPLB、DeepEP、通信计算重叠对 P95/P99 TPOT 很重要。

### 对吞吐

- 是超大 MoE 模型扩展的核心手段；
- 每 GPU 只保存部分 experts，可使用更多 GPU 承载更多专家和 batch；
- 吞吐取决于路由均衡、网络带宽、top-k 和 expert kernel；
- `top-k=2` 时，发送的 token-expert work 数约为 `2×T`。

### 对 KV Cache

- EP 不直接切 Attention KV Cache；
- 专家权重显存下降后，会间接留下更多 HBM 给 KV pool；
- 若要在一个 expert 内继续切 `H/intermediate`，那是 Expert Tensor Parallel，而不是普通 EP。

## 11. 根据瓶颈选策略

| 观察到的问题 | 优先排查/考虑 |
|---|---|
| 高负载 Queue Time、P95 TTFT 高 | DP、DPA、扩容、路由与调度 |
| 长 Prompt 的 Prefill 时间高 | PCP；也可评估 TP、chunked prefill、P/D 分离 |
| 单请求长 KV 在一张 GPU 放不下 | 多卡 DCP；单卡用 KV 量化/offload/压缩 |
| 并发请求多，KV pool 很快满 | DPA、DP、DCP、KV dtype 调优 |
| 模型权重单卡放不下 | TP、PP；MoE 模型考虑 EP |
| MoE expert 权重巨大 | EP |
| Decode TPOT 被 KV 读取限制 | DCP、KV 量化、更优 Attention kernel |
| Decode TPOT 被 collective 限制 | 降低 TP/DCP/EP 通信范围，优化拓扑与 overlap |
| 吞吐高但 P95 ITL 很差 | 检查 Prefill 干扰、DP/EP负载不均、pipeline bubble |
